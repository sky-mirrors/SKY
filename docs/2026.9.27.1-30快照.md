## 七、E-5「慢速 body 掐断」亲验记录（2026-09-27，三臂对照）

**背景**：`65b93b3` 修 E-5 时，因内网端点被 `safeFetch` 拒绝而**未能实测**，当时标注为"结构性修复 + typecheck 覆盖"。本节补上实测。

**前置事实（已核实）**：`src\electron\...` 侧 `safeFetch`（`electron\ipc-handlers.ts:171`）在 `:187` 抛「不允许访问内网保留地址」，`http:fetch` 正走它（`:975`）⇒ **本机 loopback 无法作为被测端点**（此前只是推断，现已核实）。

**实验设计**：用公网 `https://httpbin.org/drip?duration=10&numbytes=20`（该端点先回响应头、再在 10s 内滴出 body），经渲染进程 `window.electronAPI.httpFetch` 发起，取三臂。

| 臂 | 端点 / 超时 | 耗时 | 结果 | 作用 |
|---|---|---|---|---|
| **C 对照** | `/get` + 6000ms | **1044ms** | `success:true`，status 200，body 198B | 证明"连接 + 响应头"仅约 1s |
| **B 对照** | `/drip?duration=10` + 30000ms | **10629ms** | `success:true`，status 200，body **20B（完整）** | 证明该端点 body 确需约 10s |
| **A 被测** | `/drip?duration=10` + 6000ms | **6019ms** | `success:false`，error **`HTTP请求超时(6000ms)`**，body 0B | 超时精确在 6.0s 掐断 |

**判据链**：C 证明头部 ~1s 到达；B 证明 body ~10.6s 才读完；A 在 1s 与 10.6s **之间**的 6.0s 处被掐断 ⇒ **掐断点必然落在 body 读取阶段**，而非连接/响应头阶段。

**结论**：修复后的行为符合设计——**超时覆盖到 body 读取**。修复前（`clearTimeout` 紧跟 `await safeFetch`）预期 A 臂会在 ~10.6s 后 `success:true` 返回完整 body，而非 6.0s 超时。**E-5 由"未实测"转为"已实测通过"。**

**残留不确定性（如实标注）**：本实验经由 `http:fetch` 这一路径验证了 body 段超时生效；`llm:chatCompletion`/流式的 body 超时依赖 `AbortSignal.timeout`（同一机制），本次未单独复跑。

## 八、H-9 / H-10 亲验记录（2026-09-27）

**前置更正**：快照原把 H-10 的证据指向 `pluginRegistry.ts:149` 置 zombie——**实测该文件 `grep zombies` 零命中**，zombie 机制实际位于 `src\host\kernelRegistry.ts`（`zombies` Set 声明于 `:46`）。故以下按**实测文件**核，行号以本轮实测为准。

### H-9 `mountPack` 无并发互斥 —— **坐实（真未修）**
- 守卫与落记录分离：`src\host\pack\loader.ts:281` `if (this.mounted.has(packId))` → `:405` `this.mounted.set(packId, {...})`，**两者之间是整段 `await`**（异步挂载）。并发两次 `mountPack(packId)` 可在任一方 `set` 之前双双通过 `has` 检查 ⇒ **记录被覆盖 / 卸载泄漏**（TOCTOU）。
- 串行链不覆盖 mount：`:460-461` `this.reloadChain = this.reloadChain.then(run, run)` **只包 `reloadPack`**；`mountPack`(`:277`) 与 `unmountPack`(`:423`) **均未入链** ⇒ mount 与 unmount 之间同样无互斥。
- **修复方向（本轮未实施）**：为 `mountPack`/`unmountPack` 引入 per-`packId` 的 in-flight promise 表（同 id 并发调用复用或排队同一 promise），或将其统一并入 `reloadChain` 式串行链。

### H-10 僵尸插件无清除通道；`withTimeout` 不取消底层 mount —— **坐实（真未修）**
- **zombie 如何产生**：`kernelRegistry.ts:301` `this.zombies.add(k.id)`，仅在 `handleMountFailure` 中 `message.startsWith('mount-timeout')` 时触发。
- **产生后的拒绝面**：`:73`（`register`）、`:149`（`standby`）、`:176`（`getActive` 过滤）均因 zombie 而拒 ⇒ 该内核 id 不可再注册 / 待命 / 激活。
- **唯一清除点**：`kernelRegistry.ts:169` `this.zombies.delete(id)`（位于 `destroy()` 内）。而 **`destroy` / `standby` 的全仓生产调用方 grep 为空** ⇒ 实际无路可出，**只能重启**。
- **`withTimeout` 不取消底层 mount**：`pluginRegistry.ts:293-301` 的实现是 `setTimeout(() => reject(...))` + `promise.then(resolve, reject)` —— **只 reject 外层包装，既不 abort 也不调用任何取消**。故 `kernelRegistry.mountKernel`（`:294` `withTimeout(k.mount(...))`）超时后：外层判失败并把 id 标 zombie，而**底层 `mount` 仍在继续跑**；若其稍后成功，插件资源已挂载却无台账记录。
- **修复方向（本轮未实施）**：① 给 `destroy()`（或一个等价的"清除 zombie"入口）接上生产调用方（如热插拔/调试 UI 的"重置内核"）；② 让 `mount` 契约支持取消（返回 disposer 或接受 `AbortSignal`），使 `withTimeout` 能在超时时回收底层资源。

### 小结
两项**均为真缺陷，非文档过时**。本轮**只亲验、未修复**——二者都在插件/内核生命周期核心，改动面与回归风险需单独评估（且 `mount` 契约加取消会波及三个域包与内核插件的实现）。
