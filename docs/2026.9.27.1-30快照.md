## 五、前缀缓存准备度评估（用户 2026-09-27 提问）

**结论：基础设施已备（可观测 + 计价 + 前缀基本稳定），但"主动前缀缓存"未实现——按 provider 分三种情况。**

**已就绪的部分（亲验）**
- **命中度量链路完整**：`src\services\sseParser.ts:72-73` 解析 `prompt_cache_hit_tokens` / `prompt_tokens_details.cached_tokens`；`electron\streamUsage.ts:9/27` 覆盖 OpenAI 系四种形态；非流式侧 `electron\ipc-handlers.ts:1290-1291`、`src\stores\apiStore.ts:990` 同样解析。
- **真实值已透传**：`src\domains\debug\handlers.ts:46-50`（G-5 修复，此前硬编码 0）。
- **已按缓存价分档计价**：`src\benchmark\statsTracker.ts:83` 用 `cacheMissTokens * PRICE.inputUncached + cacheHitTokens * PRICE.inputCached`；`src\kernel\clusters\budget.ts:22` 亦消费 `cacheHitTokens`。
- **系统提示词是模块级常量**：`src\stores\dialogStore.ts` 的 `FIXED_SYSTEM_PROMPT`（非每请求拼接）。

**未实现 / 风险点（亲验）**
- **未发 provider 侧缓存标记**：`cache_control` / `prompt_cache` / `context_caching` / `cache_write` 全仓**零命中**。⇒ 对 **Anthropic**（需显式 `cache_control` 断点）**不会命中**；对 **OpenAI / DeepSeek**（自动前缀缓存）**被动受益**但无法主动优化。
- **tools 集合随任务变化**：`src\stores\dialogStore.ts:457` `buildMcpTools()` 先推 MCP 工具、`:487` 再 `tools.push(...NATIVE_TOOL_DEFS)`；另一路径 `:2369` 的 `activeTools` 经 `filterToolsByPlan` / 语义检索 top-N 裁剪 ⇒ **不同任务前缀不同**（同任务内应稳定，但 MCP 枚举顺序若变则同任务也会失效）。
- **`semanticCache` 不是前缀缓存**（`src\services\semanticCache.ts` 的 `lookup`/`store` 是查询→响应级），勿混为一谈。

**"仅适用于 Holo 的前缀缓存技术"落地前建议先确认**
1. 目标 provider 是**自动缓存**（OpenAI/DeepSeek，Holo 现有能力即够）还是**需显式断点**（Anthropic，需新增 `cache_control` 注入）；
2. 前缀的**稳定段边界**（system + tools 定义应固定在最前且字节稳定；动态内容一律后置——现状已把逐步提示追加到**最后一条** message，方向正确）；
3. MCP 工具枚举顺序是否需要**排序固定**（否则多轮前缀漂移）；
4. 若不改 provider 端，则可做的是**度量与告警**：用现有 `cacheHitTokens/cacheMissTokens` 加一条命中率指标，先量化再优化。
