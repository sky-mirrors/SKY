## 2. 内核纯度收编

**现状**：`scripts\purity-whitelist.json` 登记了 3 个文件的领域字面量，每条 `reason` 写明「Phase 1 应迁移未迁移；待改为运行时从已挂载 pack 收集触发域注册表（Phase 4+ 路线图跟踪）」。

**这不是遗漏，而是登记豁免**——真要做需要改内核机制：

| 步骤 | 改动点 |
|---|---|
| ① 提供正向查询口 | `packRuntime.ts` 已有 `getPackIdForDomain`（域→包），需要补「已挂载包的 domain 列表」这个反向能力 |
| ② 改 `factGuard.ts:16` | `TRIGGER_ROLES` 硬编码 Set → 运行时从 ① 收集 |
| ③ 改 `src\kernels\default\index.ts:69-71` | `detectedDomainOf`（函数定义在 `:67`）里的 `legal`/`finance`/`geotech` 域字面量 → 同 ① |
| ④ 收尾 | 每改一处从白名单删一条；`npx tsx scripts/purity-check.ts` 必须保持绿 |

> ⚠️ **易误判点（2026-10-09 复核）**：`factGuard.ts:16` 的 `TRIGGER_ROLES` 当前是 `['finance','legal','hr']`。
> 其中 **`hr` 是岗位角色、不是领域**——它比对的是 `manifest.routing.targetRoles`（词表为 `general/finance/legal/hr/sales`），
> 而 `src\data\l2Manifests.ts` 里有 **11 处** manifest 的 targetRoles 含 `hr`（简历筛选 / 入职引导 / 考勤异常 / 离职交接等）。
> 所以 `hr` **不能**随「领域收敛」一起删——删了那些 manifest 就失去 FactGuard 校验。
> 同理 `scripts\purity-whitelist.json` 中该条目的 `literal` 是 `finance/legal`（不含 `hr`）：purity 检测词表已按
> `hr → geotech` 校正（见 `a19c74d`），`hr` 本就不在检测范围内，属口径差异而非漏登记。
> 复核方式：`./node_modules/.bin/tsx scripts/purity-check.ts`（当前输出 40 files / 12 hits / 12 whitelisted / 0 unapproved）。

**影响面**：FactGuard 的触发判定 + 内核的域检测 —— 中等，且这两处都影响路由/校验行为，**需要有回归语料**（考试系统可作基线）。

## 3. Electron 33 → 44 升级

**现状**：`electron 33.4.0`（`SECURITY.md` 记着若干 High CVE）；`@electron-toolkit/utils` 锁在 33.x 决定 peer 范围。

**为什么放最后**：它动主进程**全量 API 面**（窗口 / IPC / protocol / 路径），是所有项里回归风险最高的。

**步骤**：

1. 先升 `@electron-toolkit/utils` 到 5.x（它决定 electron 的 peer 范围）
2. 再升 `electron` 到 44.x
3. 对照 Electron 34–44 的 breaking changes 清单逐条排查（重点：`remote` 相关、`webPreferences` 默认值、`protocol` API、`app.getPath` 语义）
4. **跑真机验证，不能只看单测**——`npm test` 里 30 个 spec 把 `electronAPI` 打桩（见 [60-测试与验收](60-测试与验收.md)），主进程改动它们**测不出来**：
   - `npm run smoke`（CDP 驱动真实应用，5 项断言）
   - `npm run verify:pdf` / `verify:image` / `verify:media`（真 Electron 运行时跑 sharp / ffmpeg / PDF）
5. 打包验证（见第 4 节的环境前提）

## 6. 零引用导出审计（2026-10-09 扫描）

**方法**：扫 `src/` 与 `electron/` 下所有 `export function|const|class` 名，统计其在**其他生产文件**中的词边界出现次数，测试引用单独计数。

**判据要点**（第一版探针在此处误报 35 个，修正后才收敛到 14）：

- 不能把「定义所在文件」整体排除——同文件内的引用（被同文件调用、被 `export default { ... }` 引用）必须计入，只排除**定义那一行**
- 必须区分「具名 import」与 `import * as ns`：后者使整个模块成为**命名空间接口面**，其成员即使零调用也不是死代码

**A 类：生产与测试都零引用（14 个）**

其中 **10 个在 `src\kernel\clusters\`**（`budget.ts` 的 `estimateTokenCount`/`getMode`、`cache.ts` 的 `invalidate`、`fact.ts` 的 `crossDocCheck`、`route.ts` 的 `tryDirectCommand`/`tryQuickMatch`/`checkCapability`/`classifyInputDomain`、`security.ts` 的 `shouldFactCheck`/`quickSafetyCheck`）——**不是死代码**：`registry.ts` 以 `import * as defaultRoute from './route'` 引入，`typeof defaultRoute` 即整模块类型，属「规格 6.3 五簇委托可换」的接口面。**裁定：保留。**

**真正零凭证的 4 个**（均在 `electron\`，同模块其他导出都在用，唯它们没人取）：

| 位置 | 注释声明的用途 | 实测 | 承重 / 建议 |
|---|---|---|---|
| `fileSortByType.ts:86` `knownSortFolders` | 「全部类别目录名（供 UI/文档展示）」 | UI 与文档**都没用** | 承重"未来展示"。真要展示可从同文件 `CATEGORY_BY_EXT` 派生 → 可删 |
| `pathValidator.ts:93` `initAllowedDirs` | 允许目录的注入口 | 零调用；`getAllowedBaseDirs()` 永远走 `electron.app` 兜底 | 承重"可注入性"，但无测试使用 → 删，或补一个真正用它的测试 |
| `pdfRenderer.ts:54` `disposePdfRenderer` | 「应用退出前调用」 | **零调用** | 退出清理**未接线**。进程退出时窗口由 Electron 回收，实际影响小 —— 但注释承诺 ≠ 代码事实：接线或改注释 |

## 8. 「无密钥回退规则层」的实现偏差（2026-10-09 实测）

**README 承诺**（`README.en.md` 开头「Read this first」末条 / `README.md` 同处）：

> You need your own LLM API key. Without one the app falls back to its deterministic rule layer only.
> （中文版：你需要自备 LLM API 密钥。没有密钥时，应用只回退到确定性的规则层。）

**实现**：`src\stores\dialogStore.ts:1719-1733` 在 `sendMessage` 进入路由**之前**就立了硬门禁——

- `api:is-ready` 为 false 且 `activeProviderId` / `activeModel` 未配置 ⇒
  `addSystemNotice('❌ 未配置模型网关')` + `isProcessing=false` + **`return ''`**
- 路由（`// ===== Phase A: Plan =====`）在这段判定**之后**才开始

**后果**：模型网关未配置时 **L0 / L0.5 / L1 / L2 全部不可达**。连本可 0 token 完成的纯规则请求
（如「列出桌面所有 .docx 文件」，应命中 L0「快速Shell命令」规则）也被直接拒绝。
这与项目核心主张「**在花掉 token 之前**就决定能多便宜地答完」直接冲突。

**证据**：真机 CDP 实测 `api.isReady=false`、`provider=''`、`model=''`，每条回复均为
「❌ 未配置模型网关」；`scripts\scenario-smoke.mjs` 第 0 项通过（渲染 7 条）而第 1–4 项全红。

**两个修法（需产品决策，未擅自改）**：

- **A. 门禁下移**：移到真正需要 LLM 的位置（L3 仲裁 / 执行含 `llm_generate` 的步骤之前），
  让规则层在无密钥时仍然可用 —— 兑现 README 承诺
- **B. 保留门禁、改文档**：明确写「无密钥时应用不可用」，并同步 docs/30 的 L0 台账说明

**另注**：`src\services\providerChain.ts:9` 本有「隐式 Ollama 默认端点」兜底
（`IMPLICIT_OLLAMA_PROVIDER_ID` → `http://127.0.0.1:11434`），但该门禁位于降级链**之前**，
故本机虽在运行 Ollama 也未生效。
