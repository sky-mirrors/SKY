## 1. G 系列三项：先分清「缺陷」与「取舍」

回码复核后，这三项**都不是缺陷**，各有性质差异。**不要把它们当作 bug 去"修"**。

| 项 | 现状 | 性质 | 结论 |
|---|---|---|---|
| **G-1** 消费者上下文截断 | `src\services\macroExecutor.ts:930-931` 硬编码 `nano 300 / mini 600 / pro 2000 / standard 800` 字 | token 取舍——下游步骤读上游产出的预算 | 保持现状；若要放开，走下面的「方案 A」 |
| **G-12** L0.5 排除多步 manifest | `src\services\l0SkillRouter.ts:854-861`：`isSingleStep = mode==='direct' \|\| steps.length===1`，非单步即 `return null` | 行为取舍——快配是关键词匹配，放到多步计划上有误判风险 | **先加影子模式收集数据**，不要直接放开 |
| **G-14** 指纹零容错 | `src\services\scheduleOptimizer.ts:145-175` 已做格式级归一（空白/标点/大小写），语义级刻意不做 | **已是完成态** | 无需改动 |

### G-1 可选方案（若决定放开截断）

- **方案 A（推荐）**：把三个阈值提为 `export const CONSUMER_TRUNCATE_LIMITS`，`extractStepResult` 增加**可选参数** `limits?`（缺省取常量）。
  - 好处：保持纯函数性质（无 IO），现有测试不用 mock 就能继续跑
  - 验证：现有截断测试 + 新增一条「传入自定义 limits 生效」
- **方案 B**：从 `configStore` 读。代价是给纯函数引入 IO 依赖，测试需加 mock——不推荐。
- **为什么不能直接调大常量**：`macroExecutor.ts:930-931` 的截断是 token 预算的一部分，调大等于每步多付上下文；要有实测依据（下游步骤的实际需要）再动。

### G-12 的探索路径（有风险，需前置数据）

- 现状代价：多步 manifest 每次都走到 L2，付一次 LLM 规划
- 风险：放开后关键词快配可能在多步场景误判（L0.5 的 confidence 公式见 [20-请求生命周期与路由](20-请求生命周期与路由.md)）
- 建议：**影子模式**——在 `l0SkillRouter.ts:854` 处不改变返回值，只记录「若放开会命中哪个 manifest + 置信度」，跑一段时间真实流量后看准确率，达标再切
- 参照实现：`compositeRoutingCorpus.spec.ts` 的语料回归思路（15 例真实说法）

## 2. 内核纯度收编

**现状**：`scripts\purity-whitelist.json` 登记了 3 个文件的领域字面量，每条 `reason` 写明「Phase 1 应迁移未迁移；待改为运行时从已挂载 pack 收集触发域注册表（Phase 4+ 路线图跟踪）」。

**这不是遗漏，而是登记豁免**——真要做需要改内核机制：

| 步骤 | 改动点 |
|---|---|
| ① 提供正向查询口 | `packRuntime.ts` 已有 `getPackIdForDomain`（域→包），需要补「已挂载包的 domain 列表」这个反向能力 |
| ② 改 `factGuard.ts:16` | `TRIGGER_ROLES` 硬编码 Set → 运行时从 ① 收集 |
| ③ 改 `kernels\default\index.ts:69-71` | `detectedDomainOf`（函数定义在 `:67`）里的 `legal`/`finance`/`geotech` 域字面量 → 同 ① |
| ④ 收尾 | 每改一处从白名单删一条；`npx tsx scripts/purity-check.ts` 必须保持绿 |

**影响面**：FactGuard 的触发判定 + 内核的域检测 —— 中等，且这两处都影响路由/校验行为，**需要有回归语料**（考试系统可作基线）。

## 3. Electron 33 → 44 升级

**现状**：`electron 33.4.0`（`SECURITY.md` 记着若干 High CVE）；`@electron-toolkit/utils` 锁在 33.x 决定 peer 范围。

**为什么放最后**：它动主进程**全量 API 面**（窗口 / IPC / protocol / 路径），是所有项里回归风险最高的。

**步骤**：

1. 先升 `@electron-toolkit/utils` 到 5.x（它决定 electron 的 peer 范围）
2. 再升 `electron` 到 44.x
3. 对照 Electron 34–44 的 breaking changes 清单逐条排查（重点：`remote` 相关、`webPreferences` 默认值、`protocol` API、`app.getPath` 语义）
4. **跑真机验证，不能只看单测**——`npm test` 里 30 个 spec 把 `electronAPI` 打桩（见 [60-测试与验收](60-测试与验收.md)），主进程改动它们**测不出来**：
   - `npm run smoke`（CDP 驱动真实应用，5 项断言）
   - `npm run verify:pdf` / `verify:image` / `verify:media`（真 Electron 运行时跑 sharp / ffmpeg / PDF）
5. 打包验证（见第 4 节的环境前提）

## 6. 用户验证（市场假设未验证）

**本册唯一一条非技术债——也是最缺的一条。**

| 项 | 现状 |
|---|---|
| 技术壁垒 | fail-closed 安全栈：shell 安全引擎 518 行（82 条危险模式 / 6 条可信签名 / 写盘目标解析）、路径校验、写门三态授权、FactGuard、全窗 `sandbox: true`——**难抄**（见 [40-安全模型](40-安全模型.md)） |
| 商业价值 | **未验证**。"大厂因合规成本不愿做"目前只是推测——也可能是这个市场本来就小 |
| 议程状态 | **不在本册第 1–5 节里**——那些全是技术项，没有一条是「找真实用户」 |

**技术壁垒回答"能不能被抄"，商业价值回答"值不值得做"——两个独立问题。前者有答案，后者没有。**

### 最小验证方案

- **对象**：1 个真实用户（法务 / 财务），**不是开发者**
- **动作**：用 TA 自己的 20–50 个真实文件，跑一次批量归类 / 重命名 / 格式转换
- **执行约束**：开发者在场但**不提示、不解释、不兜底**——真实用户的信任建立在他"不知道后台在干什么"之上
- **看三件事**：① 愿不愿意把文件交给它 ② 是不是比手动快 ③ 愿不愿意再来一次

| 观测 | 对应动作 |
|---|---|
| 不愿交出文件 | 问题在 UX / 告知方式，不是市场——做「处理范围可视化」再测 |
| 更快但留存低 | 价值成立、习惯没建立——评估是否做「一键重复」 |
| 会再来但不愿交文件 | 最微妙：价值成立、信任不成立——该做「沙箱预演」而非实际执行 |
| 三个都"是" | 最弱证据成立——找第二个用户复现，再谈下一步 |

> 四个分支里有两支指向"改产品"而非"改方向"——**第一次试出来多半不是"行不行"，而是"该改哪"。**
