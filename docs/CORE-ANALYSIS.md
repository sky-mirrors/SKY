# Holo 求解核心解剖：子系统机制与模型边界盲区

> 快照日期：2026-09-21。本文是开发者视角的机制层分析：先验证"小模型/大模型边界"这一架构盲区，再按子系统主线解剖后端求解核心，最后给出边界缺口总表。
> 姊妹篇：HOLO-OVERVIEW.md（产品/用户视角总览）。深度规格见：ARCHITECTURE.md、REQUEST-LIFECYCLE.md、MODEL-CAPABILITY-LEDGER-DESIGN.md（Phase A+B，状态待审阅）、LIFECYCLE-GAPS.md。

## 一、盲区验证：运行中的系统确实不知道"谁准"

### 1.1 代码证据链（八条，全部经源码核实）

| # | 证据 | 出处 |
|---|---|---|
| 1 | **tier 只是 token 预算**：nano/mini/standard/pro 四档只携带 maxTokens+temperature，每次请求无论什么档都打向唯一 `activeModel` | scheduleOptimizer.ts:309-317（G-7，项目自己认领） |
| 2 | **第二个模型只在降级链出现，且盲选**：`pickOllamaModel` 返回 `models[0]`——纯列表顺序，零能力评估 | providerChain.ts:153 |
| 3 | **无模型归属的执行记录**：路由结果按 tier 记、指纹按 manifestId 记，没有任何一处记录"这次用的是哪个具体模型" | MODEL-CAPABILITY-LEDGER-DESIGN.md 事实3 |
| 4 | **同源审计**：双引擎"第二引擎"就是同一个模型自审——3b 审 3b；且一次本地 `read_file` 要付 maxTokens 5000 的审核调用，审核比动作贵一个数量级 | dualEngineValidator.ts:262（G-6） |
| 5 | **"零 token"层藏着微 LLM 调用**：L0 文件名提取（32 tok）、意图翻译（128）、L3 仲裁（128）、消歧选号（16）——全部打给同一个模型，没有"便宜调用→便宜模型"的分工 | l0SkillRouter.ts / promptTranslator.ts（G-10） |
| 6 | **ZOL 测不到能力错配**：overkill 判定是 `actualTokens < tier上限×0.2`——弱模型输出**短而错**的答案永远不会触发"这题超纲了"的反思，反而可能因省 token 被记成功 | smartRouter.ts:324 |
| 7 | **考试判卷员也是同一个 3b 模型**：judge 走 `apiStore.chatCompletion`，判卷独立性为零 | examRunner.ts:152 |
| 8 | **降级链只往低处走**：`active provider → 其他 ollama → 隐式本地`——只有"失败后向下逃"，**没有任何"困难时向上升级"的路径** | providerChain.buildProviderChain |

### 1.2 项目知道一半：Phase A+B 承认了 1-3，但方案自带四个新盲点

MODEL-CAPABILITY-LEDGER-DESIGN.md（562 行，待审阅，未实施）的方案是**能力账本**：按 `{provider}|{modelId}|{digest8}` 建档、失败分账（exec_fail 全权重 / validation_fail 半权重）、桶化 `taskType×ctxBucket`、能力 EWMA 半衰期 7 天、ε-greedy 探索、切换成本显式定价；冷启动退化等价现状，"明文账单"章节含"fail-closed 哲学的第一道裂缝"等自我批判。

**但即使实施了 A+B，以下四点仍是盲区**（方案未认领的部分）：

- **a. 只有降级没有升级**。A+B 的三个消费点（降级链排序、流水线亲和、流水线探索）全部在"向下/向便宜"方向优化。3b 干不了的活——文件操作拒答、算术错误——没有机制路径说"这题该上云"。文档 9.7 自认：**单模型现实下 A+B 只是轻量补丁**，而现实恰是单模型（qwen2.5:3b）。
- **b. 审计独立性无解**。validation_fail 信号喂给账本，但产生信号的审计者本身还是同一个模型——账本记录的只是"3b 认为自己对不对"。
- **c. 微调用分工无解**。L0-L3 的 32/128 token 小调用是典型的"小模型活"，但架构里它们与 8192 token 重活共享同一个 activeModel。
- **d. tier（抽象档位）与账本（具体模型）的语义张力被明确推迟**给 Phase C/D："tier 说该用 standard、账本说这模型不行"谁赢、"用户偏好 vs 证据"谁赢——本阶段明确不回答（设计文档 9.6）。

### 1.3 考试实证：盲区就是当前的质量天花板

复考（09-21）可交付率 44.4% vs 及格线 80%，剩余 10 题失败**全部**归因 3b 模型能力（文件操作拒答 3 / 答非所问 2 / 算错 2 / 执行偏差 2）。系统失败归因 `failureStage` 只能启发式 + "人工复核时修正"——**系统无法自动区分"任务难"与"模型弱"**，这恰是账本想解决的事后拟合，但 unproven 冷启动期仍是硬撞墙。

### 1.4 边界问题分解为三个子问题

1. **难度→能力映射**：谁判断"这题 3b 答不动"？现状无人判断；A+B 用失败证据事后拟合，存在冷启动硬墙。
2. **代价-隐私-能力三角**：什么时候值得离开本地？现状只有失败降级、没有困难升级；"本地优先"哲学没有设计"能力不足时如何征求用户同意上云"的机制——目前以牺牲质量的方式默认回避。
3. **审核独立性**：审计者、判卷者必须与被审计者不同源。现状同源自审，A+B 未解。

## 二、后端子系统解剖（主线）

### 2.1 骨架：双子内核 + 一条真正在跑的主路径

- `src/kernel/`（契约/总线/钩子/竞争纯逻辑/漏斗编排核）+ `src/kernels/default/`（六层实现，插件化可热换）。
- **诚实备注**：微内核 `dispatch()` 五簇管线（cache→route→budget→security→llm→fact）**完整实现但无任何生产调用方**——真正跑对话的是 `route()`（漏斗）。`registerLLM` 的实际价值只是给服务层提供 `getLLM()`。这是一套"为热插拔预留但还没上车"的架构。
- 换内核状态机：drain 5s / mount 10s / zombie 永久出池；钩子三档 advisory/veto/override；veto 默认 fail-open（`holo-strict-veto` 开启才 fail-closed）。

### 2.2 六层漏斗（成本递增的求解阶梯）

| 层 | 机制 | 成本 | 门值 | 诚实备注 |
|---|---|---|---|---|
| L0 | 8 条硬编码规则（格式转换/shell/文件创建…） | 0（文件名兜底 32 tok） | 无 | "零 token"含 LLM 调用（G-10） |
| L0.5 | 纯关键词 hitRatio 匹配 | 0 | pass 0.8 / auto 0.9 | 多步 manifest 结构性排除（G-12） |
| L1 | 仅 2 条规则（模型网关/知识库） | 0 | 0.6 | **近死层**（G-11） |
| L2 | RaaP：向量+关键词双路 → RRF → 动态阈值三态门 | 0 | green 0.95 / margin 0.10 | 详见 2.3 |
| L3 | LLM 仲裁（128 tok 选号） | 128 tok | 候选≥2 | 命中置信硬编码 0.5 |
| L4 | 探索：planTask DAG 规划（≤5 步 / 8000 tok 预算） | 全额 | 无 shell 则自动执行 | 兜底层 |

配套：负反馈正则门（"不对/找不到"→跳过 L2 直降 L3）、pre-execute 否决门（veto 全量评估不短路）、空输入直达 L4、planTask DAG 校验（破环/去重）。

### 2.3 匹配算法（RaaP 核心，toolRetrieval 十步管线）

索引（本地 MiniLM-L6-v2 384 维嵌入，加载失败退伪向量）→ 路由缓存（100 条 / 30min）→ 向量 cosine + 关键词五级匹配 → 禁词否决（P1-D5）→ 否定词 ×0.3 → 反馈权重调制（mod×0.5）→ 文件加成（最高 +0.15）→ 角色加成（×1.3）→ RRF 融合（k=60，top5）→ **动态阈值**（p50/p95 分位 + 贝叶斯收缩，clamp [0.3,0.98]）→ 三态门（green 命中 / yellow 模糊 / **拒绝强行指派**）。未命中走 keyword_extract 重写再试（阈值由 ZOL 按 successRate <0.70/>0.90 自适应）。

**诚实备注**：`promptTranslator.rewriteQuery` 是恒等函数占位；旧版 `getTop3` 向量分硬编码 0.5。

### 2.4 调度与缓存（"每层机制为省 token 而存在"的落实）

- **执行指纹缓存**：输入哈希 → 整步复用；副作用工具永不复用（P1-15）；假完成清指纹防重放（P1-D4）；autoCompile 晋级要求**真实执行占比 ≥0.8**（纯缓存命中永不晋级——证据闭环）。
- **语义缓存**：`queryHash|domain|packId` 复合键（M10 杜绝跨域污染），自适应阈值 [0.80,0.95]，LRU 500。
- **并行分组**（Kahn 分批）+ **断点续跑**（checkpoint 24h 过期，容量 20）+ **脏步向下游传播**（P1-14）。
- **超时阶梯** 60/150/240/300s（绝对上限 600s）——依据 qwen2.5:3b ~10 tok/s 实测校准。**整个超时体系是为 3b 模型标定的**，换模型即失准，这是模型边界盲区在参数层的侧影。

### 2.5 模型网关（盲区最集中的子系统）

chatCompletion 九道关：就绪/熔断检查 → M20 降级链（云端→本地 Ollama，UI 无感）→ 偏好注入（`[用户偏好]` system 前缀，exam/benchmark 跳过）→ 语义缓存 → smartRoute 选档 → 预算闸 → 三种出口（Electron IPC 转发含 SSRF 防护 + IP pinning / Ollama 渲染进程直连 / Anthropic 分支）→ 超时阶梯 → 真实成本记账（actualCostOf 按 usage 计价，本地记 ¥0）。

**降级链是可用性驱动而非能力驱动**——这是第一章盲区的机制根源。

### 2.6 安全与验证（fail-closed 门卫群）

- **FactGuard V2 三层**：正则 NER（9 类实体：金额/日期/百分比/合同号/人名/公司名/银行账号/身份证/法条）→ 容差比对（金额差 >10% 即 critical；编号类不匹配即 critical）→ 跨文档校验。**5000 字窗口截断悬崖**（G-3）：长文档后半部分的数值不受保护。
- **领域约束库**：100+ 条（法律劳动/合同/财务/HR），带来源引用与测试用例；误报率 >0.3 自动停用、>0.2 降级（约束自治）。
- **投递核验 deliverableCheck**：三态 ok / no-artifact / mismatch，防"创建空文件报成功"（P1 假完成）。
- **双引擎审计**：机制上是对的（意图/参数/风险三维），但同源 + 费效倒挂（见第一章证据 4），是全系统最值得重构的一块。
- 主进程侧防线：路径校验、shell 白名单、SSRF + IP pinning、MCP env 黑名单、三级工具权限。

### 2.7 学习体系（四个学习器，全部零 token）

- **ZOL×3**（路由/重写/消歧）：outcome 三态 success/failure/overkill，每 20 次按 overkillRate 调阈值。
- **反馈权重**：👍+0.10 / 👎−0.15 / 撤销−0.20，±0.5 钳位，24h 衰减，直接改技能检索排序。
- **竞争 EMA**：α=0.1，pack 级质量，默认关闭。
- **偏好注入**：手动半环（G-16 部分修复）。

**架构师自己的诚实注脚**（G-16 原文）："机制对自己全自动，对用户全手动，且手动也不接线"——机制学习与用户学习的不对称是设计价值观的体现。

### 2.8 装配（启动 17 步、总线 58 通道 12 域）

vault 同步必须先于一切 store 实例化（否则空缓存覆盖磁盘）→ store 装载 → pipelineExecutor 注入（打破循环依赖）→ kernel 创建 → 内核插件激活 + pack 挂载 + 钩子桥 → 12 域 handlers 注册（58 通道）→ apiStore 适配为 LLM Port → 语义缓存/智能路由/指纹后装。跨模块调用全收敛到 globalBus 双平面（request 点对点 / emit 广播），域层只做"事件→store/service"薄委托。

## 三、边界缺口总表与结论

| 子系统 | 边界相关现状 | 缺口定性 |
|---|---|---|
| 网关 | tier=参数、单 activeModel | **已知已设计未实施**（G-7→A+B） |
| 降级链 | 失败触发、只降不升、盲选 | **方案未覆盖**（A+B 只优化降级方向） |
| 双引擎 | 同模型自审 + 费效倒挂 | **方案未覆盖**（审计独立性无解） |
| ZOL | 只测 token 效率 | **方案部分覆盖**（账本补能力维，但 overkill 语义仍不识"短而错"） |
| L0-L3 微调用 | 与重活共享同一模型 | **方案未覆盖** |
| 考试判卷 | 同一 3b 判卷 | **方案未覆盖** |
| tier↔账本张力 | 明确推迟给 C/D | **已知被推迟** |
| 单模型现实 | A+B 价值依赖多模型 | **已知投资风险**（设计文档 9.7 明示） |

**三层结论**：

1. **已知已设计未实施**——能力账本（Phase A+B 待审阅）解决"不知道谁准"；
2. **已知被推迟**——tier 裁决、诚实降级、map-reduce 角色分工（Phase C/D）；
3. **真正未被任何文档认领的**——升级路径（困难时上云）、审计独立性、微调用分工、判卷独立性。第 3 层连 562 行设计文档都未触及，是"模型边界盲区"最准确的所指。
