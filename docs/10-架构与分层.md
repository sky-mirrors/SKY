## 进程模型

```
electron\  （主进程）                    src\  （渲染进程）
├─ main.ts            窗口与启动          ├─ main.ts        Vue app + Pinia 初始化
├─ window-manager.ts  多窗口创建          ├─ App.vue        顶层视图（WorkbenchShell）
├─ ipc-handlers.ts    IPC 路由            ├─ services\      业务逻辑（72 个模块）
├─ shell-security.ts  shell 安全引擎      ├─ stores\        Pinia store（18）
├─ pathValidator.ts   路径读写校验        ├─ components\    Vue 组件（32）
├─ mcp-manager.ts     MCP 子进程          ├─ kernel\        漏斗编排 + 钩子 + 簇
├─ preload.ts         contextBridge       ├─ kernels\       内核插件（default / lite）
└─ <文件算子>.ts      纯计划核心          ├─ host\          热插拔宿主（插件/域/Pack）
   （fileRenameExt / fileUnzip /         ├─ domains\       领域处理器（bus 通道注册点）
     fileSortByType / fileConvertBatch）  ├─ data\          静态数据（拓扑/清单/技能目录）
                                         └─ exam\          验收考试系统
```

- 渲染进程不直接碰文件系统：一切写操作经 `preload.ts` 暴露的 `electronAPI` → 主进程 IPC。
- 文件算子是**纯计划核心**（只算「该做什么」，不执行），两侧各有一份 dispatch：渲染侧 `src\services\macroExecutor.ts`（宏路径）与 `src\stores\dialogStore.ts`（MCP 直调回路），真正干活在主进程 `electron\ipc-handlers.ts`。

## 内核装配：六层漏斗 + 钩子

`src\kernel\funnel.ts` 是**编排核**：只持有层序、门值、钩子插桩、降级与两道否决门位置；每层的默认实现由内核插件注入。

| 事实 | 值 | 位置 |
|---|---|---|
| 层序 | `['L0','L0.5','L1','L2','L3','L4']` | `src\kernel\funnel.ts:102` |
| 门值 | `{ l05Pass: 0.6, l05Auto: 0.9, l1Pass: 0.6 }` | `src\kernel\funnel.ts:36` |
| 逐层 dispatch | 按 `LAYER_ORDER` 顺序求值，逐层失败降级 | `src\kernel\funnel.ts:190-191` |
| 否决门位置 | 只有两处：`pre-execute` / `pre-output` | `src\kernel\hooks.ts:12` |
| 层默认实现 | 内核插件注入，可被 override 钩子替换 | `src\kernels\default\index.ts` |

**钩子三态** `[已复核]`

| 态 | 作用 | 能否否决 |
|---|---|---|
| advisory | 影响打分（`scoreDelta`） | 否 |
| veto | 在 `pre-execute` / `pre-output` 两处拦 | 是 |
| override | 替换整层实现 | — |

领域钩子只能经 advisory 影响打分，不能直接改门值。

## 三层热插拔

| 层 | 宿主 | 装载物 |
|---|---|---|
| 内核 | `src\host\kernelRegistry.ts` | 整个漏斗实现（默认 / lite） |
| 领域 | `src\domains\<域>\handlers.ts` | 领域处理器（bus 通道注册点） |
| Pack | `src\host\pack\loader.ts` | 领域能力包（约束 + 知识 + 执行） |

**Pack 四阶段挂载** `[已复核]`：`manifest → knowledge → boundary → execution`，**任一层失败全量回滚**（`loader.ts`）。

机制要点（回码核对过的几条）：

| # | 机制 | 现状 | 位置 |
|---|---|---|---|
| M5 | 逐层 dispatch | 钩子收集 → 顾问 → 合并 → 覆盖 → 门评估 → 否决门 → 簇定点 | `src\kernel\funnel.ts:109-191` |
| M6 | 否决门 | 仅 `pre-execute` / `pre-output` 两道 | `src\kernel\hooks.ts:12` |
| M8 | Pack 加载器 | 事务式分层加载，失败逆序全量回滚 | `src\host\pack\loader.ts` |
| M14 | 运行时权限校验 | manifest 能力快照进缓存，校验失败**跳过 + warning，永不抛入主流程** | `src\host\pluginRegistry.ts:71` |
| M15 | 请求级快照 | dispatch 开始时捕获簇引用，在途请求全程用同一组；热换只影响下一个请求 | `src\kernel\hooks.ts:89`、`src\kernel\clusters\registry.ts:53`、`src\kernel\index.ts:59` |
| M16 | 竞争评分与影子评估 | **默认关**（`competitiveMode` flag），关闭时零开销 | `src\kernel\competition.ts`、`src\kernels\default\index.ts` |
| M18 | 内核纯度 CI | `scripts\purity-check.ts` + `pure-services.list` + `purity-whitelist.json` | 三个文件均在盘 |

> 更细的 M1–M20 设计规格（含评审稿与实施修订记录）已随旧文档删除；需要追溯时走 [README 的 git 追溯通道](README.md#历史追溯)。**引用规格书里的目标态设计时必须回代码验证**——规格书自述为「评审稿」，其中门值等细节与现行代码不符（例：它写 L0.5 门 0.8，现行是 0.6）。

## 领域包

Pack 装载机制见上「三层热插拔」。数据源两路：`src\host\pack\loader.ts:122` `createBuiltinPackSource()`（编译期 `import.meta.glob` 收集内置目录）与 `src\host\pack\userPackSource.ts:86` `createUserPackSource()`（用户目录，纯数据），由 `userPackSource.ts:133` `createHybridPackSource()` 合成，**内置优先**。本仓库当前**不带内置 pack 内容**，实际挂载的 pack 全部来自用户目录。

用户 pack 是**纯数据**：`listEvaluators` 恒为空（TS evaluator 是编译期模块，运行时无法从磁盘加载）——需要自定义评测逻辑时用 constraints 的 DSL。

装载入口：`src\host\packRuntime.ts` 的 `installUserPacks()` 读 `{userData}\holostarmap-packs\`（userData 经 `window.electronAPI.getUserDataPath()` 取得，与 `pack:user:root` IPC 同源）。`[已复核 2026-10-09]`

注：该目录名**刻意保留了改名前的 `holostarmap-packs`**，未随品牌改成 `sky-packs`——它在 userData 内，改名会让用户已安装的包失效，而收益仅是命名一致。

**缺口**（已回码）：

1. **第三方包的信任与分发未设计**：Pack 可挂 `override` 钩子到任意层（等于改写路由与执行），而 loader 只做 schema 与冲突校验。能力分级（知识 / 声明式 / 可信）的建议见旧设计文（已删，走 git 追溯）。
